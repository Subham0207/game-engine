# FlowScript Notes

This file documents the recent FlowScript changes and how the compile step works.

## Recent changes

- Added an Execute button to the FlowScript UI and wired it to run the compiled Lua chunk.
- Added a small Lua log panel in the FlowScript UI. Lua `print(...)` output is captured and shown here.
- Added a layered compile pipeline:
  - `Flowscript::Compile::Compiler` builds an intermediate representation (IR) from nodes/links.
  - `LuaEmitter` converts IR into Lua source.
- Added compile diagnostics surfaced through `FlowScript::getCompileDiagnostics()` and logged as `[COMPILE] ...` lines.
- Added `FlowScript::deCompile` to rebuild a node graph from supported Lua.
- Refactored decompile into focused components under `FlowScript/Decompile`:
  - `LuaSubsetLineParser` for line-level Lua subset parsing.
  - `DecompileGraphBuilder` for node/link reconstruction and execution-chain wiring.
  - `Helpers` for shared utility logic (trim/prefix/literal/operator split helpers).
- `FlowScript::deCompile()` is now orchestration-only: parse line -> apply statement -> finalize.

## How compilation works now (`FlowScript::compile`)

`FlowScript::compile()` is now an orchestrator, not a monolithic code generator.

1) Build IR from graph
- `FlowScript::compile()` creates a `Flowscript::Compile::Compiler` instance.
- It calls `Compiler::Compile(nodes, nodeGraphLinks)`.
- The compiler builds graph indexes (pin ownership + data/exec connectivity), validates links/required inputs, and produces:
  - `statements` (IR nodes), and
  - `diagnostics` (warnings/errors about invalid or incomplete graph wiring).

2) Compiler internals (high-level)
- **Graph indexing** (`GraphIndexLookup.hpp`):
  - Maps `pinId -> PinInfo`.
  - Splits links into data links and execution links.
  - Builds data dependency graph and execution adjacency.
- **Validation pass** (`Compiler.cpp`):
  - Unknown pin references.
  - Invalid link direction/type combinations.
  - Missing required inputs for known node kinds.
- **IR generation** (`Compiler.cpp`, `Statement.hpp`, `Expression.hpp`):
  - Data nodes -> expression/local assignment IR.
  - Exec nodes (`Function`, `Print`, `Return`, plus exec-capable operators) -> statement IR.
  - Generic object nodes (`GenericType(name)`) emit table creation + field assignments in IR.

3) Emit Lua from IR
- `FlowScript::compile()` calls `LuaEmitter::Emit(result.statements)`.
- `LuaEmitter` handles expression and statement serialization with indentation.
- Function bodies are emitted as:
  - `local node_<id> = function()`
  - body statements
  - `end`

4) Save output + diagnostics
- `compiledLua` is set to:
  - `-- Generated by FlowScript::compile()\n` + emitted Lua.
- Compiler diagnostics are stored in `compileDiagnostics`.
- Each diagnostic is also appended to the UI log as `[COMPILE] <message>`.

### Important behavior changes from the old compiler path

- No legacy inline string-emission traversal inside `FlowScript::compile()`.
- No old "terminal auto-return" synthesis at the end of compile.
- Compile is now split into clear layers: **graph resolution -> validation -> IR build -> Lua emit**.

## How de-compilation works (`FlowScript::deCompile`)

`deCompile` parses a limited Lua subset (the patterns emitted by the compiler/emitter) and rebuilds nodes/links.
If it encounters unsupported Lua, it throws a runtime error.

Current decompile pipeline:
- `FlowScript::deCompile()` (`Glitter/Sources/FlowScript.cpp`) creates:
  - `Flowscript::Decompile::LuaSubsetLineParser`
  - `Flowscript::Decompile::DecompileGraphBuilder`
- For each Lua line:
  - parser returns `ParsedStatement` (or skips comments/blank lines)
  - builder `apply(...)` mutates graph state (nodes/links/function scopes/pending generic objects)
- After iteration, `builder.finalize()` flushes pending generic objects, validates function-scope balance, and links top-level execution chain.

Primary decompile files:
- `Glitter/Headers/NodeGraph/FlowScript/Decompile/ParsedStatement.hpp`
- `Glitter/Headers/NodeGraph/FlowScript/Decompile/LuaSubsetLineParser.hpp`
- `Glitter/Headers/NodeGraph/FlowScript/Decompile/DecompileGraphBuilder.hpp`
- `Glitter/Headers/NodeGraph/FlowScript/Decompile/Helpers.hpp`
- `Glitter/Sources/FlowScript/Decompile/LuaSubsetLineParser.cpp`
- `Glitter/Sources/FlowScript/Decompile/DecompileGraphBuilder.cpp`

Supported statements and mappings:
- `local node_x = <number>` -> `Integer` node with field set.
- `local node_x = <true|false>` -> `Boolean` node with field set.
- `local node_x = (<a> + <b>)` -> `Add` node with inputs linked.
- `local node_x = (<a> - <b>)` -> `Subtract` node with inputs linked.
- `local node_x = (<a> > <b>)` -> `GreaterThan` node with inputs linked.
- `local node_x = (<a> == <b>)` -> `EqualsTo` node with inputs linked.
- `local node_x = (<a> ~= <b>)` -> `NotEqualsTo` node with inputs linked.
- `print("[LUA]", <expr>)` -> `Print` node in exec flow.
- `return <expr>` -> `Return` node in exec flow (single input only).
- `local node_x = function()` ... `end` -> `Function` node and exec chain.
- `local <object> = {}` with `<object>.<field> = <literal>` -> `GenericType(<object>)` node with field outputs.

Execution flow reconstruction:
- `Function` blocks create a `Function` node and link its exec output to the first
  exec statement inside the block.
- Inside a function, `Print`, `Return`, and currently supported exec-capable operator nodes are appended in source order and linked through exec pins.
- At top level (outside functions), exec statements are linked in source order.

Data value resolution:
- `<expr>` can be a literal number/boolean or a previously defined `node_<id>` variable.
- Generic object field refs (`object.field`) are supported when rebuilt from a `GenericType(object)` block.
- Unsupported literals (strings, tables, etc.) cause a throw.

Limitations:
- `return { ... }` is not supported.
- No attempt is made to parse arbitrary Lua; only the supported subset is accepted.

Build-system note:
- `CMakeLists.txt` now includes `Glitter/Sources/*/*/*/*.cpp` in `PROJECT_SOURCES` so nested decompile sources under `Glitter/Sources/FlowScript/Decompile/` are compiled automatically.

## Notes

- `Print` is part of the execution flow, so its exec output can chain to the next node.
- The FlowScript UI console shows runtime `print(...)` output and compile diagnostics.
- If you want a single, global log, move the print-handler setup out of the Execute button.
